В GitLab CI/CD «выпадающие списки» обычно означают возможность выбора значения переменной из заранее заданного набора при ручном запуске пайплайна (кнопка «Run pipeline»). Это удобно, когда нужно, чтобы пользователь выбрал окружение, версию, параметры деплоя и т.п. из ограниченного списка.

GitLab поддерживает такие списки через переменные с типом select. Настроить их можно двумя способами:

1. В самом файле .gitlab-ci.yml — с помощью секции variables и ключа options.
2. Через веб-интерфейс проекта/группы — в разделе Settings → CI/CD → Variables, указав тип переменной select.

Оба способа дают одинаковый результат: при ручном запуске пайплайна рядом с полем переменной появится выпадающий список.

---

1. Настройка выпадающего списка в .gitlab-ci.yml

В GitLab 13.3+ можно описать переменные с атрибутами description, value и options в корневом блоке variables. Это работает только для переменных, которые видны при ручном запуске (manual pipeline).

Пример .gitlab-ci.yml:

```yaml
variables:
  DEPLOY_ENV:
    value: "staging"
    description: "Выберите окружение для деплоя"
    options:
      - "staging"
      - "production"
      - "development"
  VERSION:
    value: "1.0.0"
    description: "Версия релиза"
    options:
      - "1.0.0"
      - "1.1.0"
      - "2.0.0"

stages:
  - deploy

deploy_job:
  stage: deploy
  script:
    - echo "Деплой на окружение $DEPLOY_ENV, версия $VERSION"
```

Когда вы нажмёте Run pipeline в интерфейсе GitLab, для каждой из этих переменных появится выпадающий список с указанными значениями. Значение по умолчанию — то, что задано в value.

Важные замечания:

· Такие переменные имеют область видимости только при ручном запуске. В автоматических пайплайнах (по push, merge request и т.д.) они будут использовать значение value по умолчанию.
· Атрибут options может быть списком строк.
· Если вы хотите, чтобы список был обязательным для выбора, можно оставить value пустым или вовсе не указывать, но тогда потребуется выбрать значение вручную при запуске.

---

2. Настройка через веб-интерфейс GitLab

Этот способ удобен, когда нужно задать переменную на уровне проекта или группы, и она будет доступна во всех пайплайнах, не изменяя .gitlab-ci.yml.

Шаги:

1. Откройте ваш проект в GitLab.
2. Перейдите в Settings → CI/CD → Variables.
3. Нажмите Add variable.
4. Заполните поля:
   · Key — имя переменной (например, DEPLOY_ENV).
   · Value — значение по умолчанию (можно оставить пустым, если хотите, чтобы пользователь всегда выбирал сам).
   · Type — выберите Select (ранее Environment или Variable).
   · Options — введите список возможных значений (каждое с новой строки).
   · При необходимости отметьте флажки Protect variable, Mask variable, Expand variable reference.
5. Сохраните.

После этого при ручном запуске пайплайна для этой переменной появится выпадающий список.

Пример заполнения в UI:

```
Key: DEPLOY_ENV
Value: staging
Type: Select
Options:
staging
production
development
```

---

3. Ограничения и советы

· Область видимости: переменные с options из .gitlab-ci.yml не наследуются дочерними пайплайнами, если они запускаются автоматически. Для передачи выбранных значений в дочерние пайплайны используйте trigger с forward или передавайте явно.
· Защищённые переменные: если переменная защищена (protected), выпадающий список будет показан только при запуске с защищённой ветки/тега.
· Использование в rules: значения таких переменных можно использовать в rules:if для условного выполнения джобов.
· Совместимость версий: функция options в variables блока .gitlab-ci.yml появилась в GitLab 13.3. В GitLab 14.x и выше работает стабильно. Если у вас версия ниже, используйте только настройку через UI (там поддержка select-переменных появилась раньше).
· Безопасность: не храните секретные значения в options, так как они будут видны всем, кто может запускать пайплайн вручную.

---

4. Пример использования выпадающего списка для выбора окружения

Допустим, у вас есть три окружения: dev, staging, prod. Вы хотите, чтобы при ручном деплое можно было выбрать окружение, и джоба выполнялась только для выбранного.

.gitlab-ci.yml:

```yaml
variables:
  TARGET_ENV:
    value: "dev"
    description: "Окружение для деплоя"
    options:
      - "dev"
      - "staging"
      - "prod"

deploy:
  stage: deploy
  script:
    - echo "Deploying to $TARGET_ENV"
    - ./deploy.sh $TARGET_ENV
  environment:
    name: $TARGET_ENV
```

При ручном запуске пайплайна вы увидите выпадающий список с тремя окружениями, выбранное значение попадёт в переменную TARGET_ENV и будет использовано в скрипте и в имени окружения.

Заключение

Выпадающие списки для переменных в GitLab CI/CD — это простой и эффективный способ дать пользователям контролируемый выбор параметров при ручном запуске. Настроить их можно как декларативно в .gitlab-ci.yml (начиная с GitLab 13.3), так и через веб-интерфейс. Используйте эту возможность, когда нужно ограничить ввод и избежать ошибок.

Если ваш вопрос был о другом типе «выпадающих списков» (например, автодополнение в редакторе или выбор шаблона), уточните, пожалуйста, — и я дополню ответ.

В GitLab CI/CD выпадающие списки для переменных (тип select) задаются статически: либо через ключ options в .gitlab-ci.yml, либо через веб-интерфейс в настройках CI/CD. Напрямую загрузить список значений из файла в репозитории или внешнего источника невозможно, потому что GitLab интерпретирует .gitlab-ci.yml до запуска пайплайна и не выполняет динамическое чтение файлов для построения UI.

Однако существуют обходные пути, позволяющие автоматически поддерживать актуальность выпадающего списка на основе файла.

---

1. Автоматическое обновление переменной через GitLab API (рекомендуемый способ)

Вы можете создать scheduled pipeline (или запускать вручную), который читает нужный файл из репозитория, извлекает список значений и обновляет переменную типа select через GitLab API. Тогда при следующем ручном запуске основного пайплайна в выпадающем списке будут свежие данные.

Шаги:

1. Создайте переменную в настройках проекта (Settings → CI/CD → Variables) с типом Select и любым первоначальным списком.
   · Key: DEPLOY_ENV
   · Value: staging (значение по умолчанию)
   · Type: Select
   · Options: staging (позже обновится автоматически)
2. Сохраните файл со списком значений в репозитории, например environments.txt:
   ```
   development
   staging
   production
   ```
3. Добавьте в .gitlab-ci.yml джобу для обновления переменной (можно запускать по расписанию или вручную). Для доступа к API понадобится токен с правами api (например, personal access token или project access token).
   ```yaml
   update_select_options:
     stage: .pre
     image: alpine:latest
     script:
       - apk add --no-cache curl jq
       - |
         # Читаем файл, преобразуем строки в JSON-массив
         OPTIONS_JSON=$(cat environments.txt | jq -R -s -c 'split("\n") | map(select(length > 0))')
         echo "Options: $OPTIONS_JSON"
         
         # Формируем payload для API
         PAYLOAD=$(jq -n \
           --arg value "staging" \
           --argjson options "$OPTIONS_JSON" \
           '{value: $value, options: $options}')
         
         # Обновляем переменную через API
         curl --request PUT \
           --header "PRIVATE-TOKEN: $GITLAB_API_TOKEN" \
           --header "Content-Type: application/json" \
           --data "$PAYLOAD" \
           "https://gitlab.com/api/v4/projects/$CI_PROJECT_ID/variables/DEPLOY_ENV"
     only:
       - schedules
   ```
   Пояснения:
   · jq -R -s -c 'split("\n") | map(select(length > 0))' читает каждую строку файла, убирает пустые строки и формирует JSON-массив.
   · $GITLAB_API_TOKEN — переменная CI/CD, содержащая токен с правами api (храните её как защищённую/маскированную).
   · CI_PROJECT_ID — встроенная переменная с ID проекта.
   · Джоба выполняется только по расписанию (only: schedules), чтобы не замедлять обычные пайплайны.
4. Настройте расписание (CI/CD → Schedules) для регулярного обновления (например, раз в сутки или после изменения файла).

Теперь при ручном запуске основного пайплайна выпадающий список DEPLOY_ENV будет содержать значения из environments.txt.

---

2. Использование дочерних пайплайнов с динамической генерацией .gitlab-ci.yml

Если вы хотите, чтобы список зависел от файла в момент ручного запуска, можно создать родительский пайплайн, который генерирует дочерний конфиг с нужными options, читая файл. Но сам ручной запуск родительского пайплайна не покажет выпадающий список для дочернего (пользователь увидит только переменные родительского). Это менее удобно.

---

3. Использование переменной типа File + выбор в рантайме

Вместо выпадающего списка можно передать содержимое файла как переменную типа File и в скрипте выбрать нужное значение (например, через интерактивный prompt или аргумент). Это не настоящий dropdown, но позволяет избежать жёсткого кодирования.

Пример .gitlab-ci.yml:

```yaml
variables:
  ENV_LIST_FILE: "environments.txt"   # файл должен существовать в репозитории

deploy:
  script:
    - cat $ENV_LIST_FILE
    - echo "Выберите окружение из списка выше"
    # Здесь можно использовать read или выбрать через аргумент джобы
```

---

4. Внешние триггеры с параметрами

Вы можете запускать пайплайн через API с передачей нужного значения (из любого источника, включая файл). В этом случае выпадающий список не требуется, т.к. значение уже выбрано внешней системой.

```bash
curl --request POST \
  --header "PRIVATE-TOKEN: $TOKEN" \
  --form "ref=main" \
  --form "variables[DEPLOY_ENV]=production" \
  "https://gitlab.com/api/v4/projects/$PROJECT_ID/pipeline"
```

---

Ограничения и советы

· GitLab не поддерживает динамическое чтение файлов для построения options в .gitlab-ci.yml или UI.
· Переменные типа select, объявленные в .gitlab-ci.yml, переопределяют переменные из UI при ручном запуске (если обе существуют).
· Для автоматического обновления через API необходимо хранить токен с минимально необходимыми правами (api) и защитить его.
· Если файл с опциями меняется редко, можно обновлять переменную вручную через UI, но автоматизация экономит время.

Таким образом, хотя прямой загрузки из файла нет, вы можете легко синхронизировать выпадающий список с содержимым файла, используя scheduled pipeline и GitLab API.

В GitLab CI/CD невозможно напрямую загрузить значения для выпадающего списка (select) из внешнего источника, например из Ansible inventory, расположенного в другом проекте. Но вы можете автоматизировать обновление переменной типа select через GitLab API, используя scheduled pipeline, который будет:

1. Получать inventory из нужных проектов.
2. Извлекать из него списки хостов, групп, переменных и т.д.
3. Обновлять переменную (или несколько переменных) с типом Select, чтобы при следующем ручном запуске пайплайна в выпадающем списке были актуальные значения.

Ниже — подробная инструкция, как это реализовать.

---

1. Создайте переменную типа Select в настройках проекта

Перейдите в Settings → CI/CD → Variables и добавьте переменную, например:

· Key: ANSIBLE_HOST
· Value: (значение по умолчанию, например, all)
· Type: Select
· Options: (пока можно указать одно значение-заглушку, позже обновится)

Сохраните переменную.

Если нужно несколько выпадающих списков (например, для выбора группы и хоста), создайте несколько переменных.

---

2. Подготовьте скрипт для обновления переменной

В вашем репозитории создайте, например, файл update_ansible_options.sh или встройте команды прямо в джобу .gitlab-ci.yml. Мы рассмотрим вариант с использованием Docker-образа, содержащего ansible, jq, curl и git.

Пример джобы в .gitlab-ci.yml:

```yaml
stages:
  - update-options

update_ansible_hosts:
  stage: update-options
  image: alpine:latest   # или специализированный образ с ansible
  before_script:
    - apk add --no-cache git ansible jq curl
  script:
    # 1. Клонируем репозитории с inventory (если они в отдельных проектах)
    - git clone https://gitlab-ci-token:${CI_JOB_TOKEN}@gitlab.example.com/group/ansible-inventory.git inventory
    # Если inventory в том же проекте, можно использовать $CI_PROJECT_DIR

    # 2. Генерируем JSON из inventory
    - ansible-inventory -i inventory/hosts --list > inventory.json

    # 3. Извлекаем список хостов (например, все хосты)
    - HOSTS=$(jq -c '[.all.hosts[]] | map(select(. != "localhost"))' inventory.json)
      # или из групп: jq -c '[._meta.hostvars | keys[]]'

    # 4. Обновляем переменную через API
    - |
      PAYLOAD=$(jq -n \
        --arg value "all" \
        --argjson options "$HOSTS" \
        '{value: $value, options: $options}')

      curl --request PUT \
        --header "PRIVATE-TOKEN: $GITLAB_API_TOKEN" \
        --header "Content-Type: application/json" \
        --data "$PAYLOAD" \
        "https://gitlab.example.com/api/v4/projects/$CI_PROJECT_ID/variables/ANSIBLE_HOST"
  only:
    - schedules   # или можно запускать вручную при необходимости
```

Пояснения:

· ansible-inventory --list выводит полную структуру в JSON. Вы можете выбрать нужные данные:
  · Все хосты: .all.hosts (список) или ._meta.hostvars (ключи).
  · Список групп: .all.children или ключи верхнего уровня, кроме _meta и all.
  · Переменные группы: .group_name.vars.
· jq используется для преобразования в JSON-массив строк, который ожидает API.
· Для клонирования других проектов используется CI_JOB_TOKEN, который имеет доступ только к проектам в той же группе/подгруппе. Если нужно больше прав, используйте персональный токен или project access token.
· $GITLAB_API_TOKEN — переменная CI/CD (masked, protected) с токеном, имеющим права api на этот проект.

---

3. Настройка доступа к другим проектам

Если inventory хранится в другом проекте, убедитесь, что у джобы есть права на его чтение:

· Если проекты в одной группе, CI_JOB_TOKEN обычно достаточно (если не запрещено настройками).
· В противном случае создайте Project Access Token (Settings → Access Tokens) в том проекте, где лежит inventory, с правами read_repository. Сохраните его в переменной INVENTORY_READ_TOKEN и используйте при клонировании:
  ```bash
  git clone https://oauth2:${INVENTORY_READ_TOKEN}@gitlab.example.com/group/ansible-inventory.git
  ```

Если inventory находится в том же проекте, просто используйте $CI_PROJECT_DIR без клонирования.

---

4. Запуск по расписанию

Чтобы список всегда был актуальным, настройте CI/CD → Schedules для регулярного запуска джобы (например, раз в час или раз в день). Также можно запускать её вручную через интерфейс (Run pipeline) или при изменении inventory (например, через trigger от другого пайплайна).

---

5. Обработка нескольких выпадающих списков

Если вам нужно несколько связанных списков (например, сначала выбрать группу, потом хост из этой группы), то GitLab не поддерживает каскадные списки на этапе ручного запуска. Возможные обходные пути:

1. Создать один список с комбинированными значениями, например "group:host":
   ```yaml
   OPTIONS=$(jq -c '[.all.children | to_entries[] | .key as $g | .value.hosts[]? | "\($g):\(.)"]' inventory.json)
   ```
   Пользователь выберет, например, webservers:web01, а в джобе вы разделите значение на группу и хост.
2. Выполнять выбор в рантайме — передать только имя группы через переменную, а внутри джобы с помощью ansible или jq выбрать конкретный хост (например, через --limit или подстановку). Но тогда не будет выпадающего списка хостов.
3. Использовать внешний веб-интерфейс (например, собственный сервис), который через API запускает пайплайн с уже выбранными параметрами.

---

6. Пример полного скрипта с извлечением групп, хостов и переменных

Допустим, вы хотите обновить две переменные: ANSIBLE_GROUP (список групп) и ANSIBLE_HOST (список всех хостов). Вот расширенный пример:

```yaml
update_ansible_options:
  stage: update-options
  image: alpine:latest
  before_script:
    - apk add --no-cache git ansible jq curl
  script:
    - git clone https://gitlab-ci-token:${CI_JOB_TOKEN}@gitlab.example.com/group/ansible-inventory.git inv
    - cd inv
    - ansible-inventory -i hosts --list > inventory.json

    # Группы (все, кроме _meta и all)
    - GROUPS=$(jq -c '[keys[] | select(. != "_meta" and . != "all")]' inventory.json)

    # Хосты (все хосты из _meta.hostvars)
    - HOSTS=$(jq -c '[._meta.hostvars | keys[]]' inventory.json)

    # Функция обновления переменной
    - |
      update_var() {
        local var_name=$1
        local default_value=$2
        local options=$3
        local payload=$(jq -n --arg value "$default_value" --argjson options "$options" '{value: $value, options: $options}')
        curl --request PUT \
          --header "PRIVATE-TOKEN: $GITLAB_API_TOKEN" \
          --header "Content-Type: application/json" \
          --data "$payload" \
          "https://gitlab.example.com/api/v4/projects/$CI_PROJECT_ID/variables/$var_name"
      }

    - update_var "ANSIBLE_GROUP" "all" "$GROUPS"
    - update_var "ANSIBLE_HOST" "all" "$HOSTS"
  only:
    - schedules
```

---

7. Важные замечания и ограничения

· Безопасность: Переменная $GITLAB_API_TOKEN должна быть защищена (masked, protected) и иметь минимально необходимые права (api только на этот проект). Никогда не храните её в открытом виде в репозитории.
· Размер списка: GitLab UI может плохо отображать очень большие списки (сотни элементов). Если инвентори содержит много хостов, рассмотрите возможность выбора группы или использование комбинированных значений.
· Формат inventory: Ansible поддерживает INI, YAML, динамические inventory. ansible-inventory --list работает со всеми, если установлены необходимые плагины (например, для облачных инвентори).
· Версии: Убедитесь, что в Docker-образе установлены совместимые версии Ansible и jq. Можно использовать официальный образ cytopia/ansible или alpine + пакеты.

---

Альтернативный подход без выпадающего списка

Если автоматизация через API кажется сложной, вы можете передавать нужные параметры через переменные окружения при запуске пайплайна по API (curl) или из другого CI/CD. Тогда не нужен выпадающий список, но пользователь должен сам знать возможные значения.

Пример запуска с параметрами через API:

```bash
curl -X POST \
  --header "PRIVATE-TOKEN: $TOKEN" \
  --form "ref=main" \
  --form "variables[ANSIBLE_GROUP]=webservers" \
  --form "variables[ANSIBLE_HOST]=web01" \
  "https://gitlab.example.com/api/v4/projects/$PROJECT_ID/pipeline"
```

Заключение

Прямая загрузка значений для выпадающего списка из Ansible inventory в .gitlab-ci.yml невозможна, но с помощью scheduled pipeline и GitLab API вы можете автоматически синхронизировать переменные типа Select с данными из любых проектов. Это позволяет при ручном запуске пайплайна выбирать нужные хосты, группы или другие параметры из актуального inventory.
